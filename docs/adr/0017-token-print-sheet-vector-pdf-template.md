# Token Print Sheets are a committed vector PDF template stamped by pdf-lib, not a rendered SVG

**Status:** accepted — implements the deferred "batch/sheet UI is Phase 2" step of [ADR 0015](./0015-qr-code-assignment.md) for [Token cards], and deliberately *diverges* from [ADR 0013](./0013-self-print-pdf-client-side-multi-up-logo-less.md)'s rasterize-to-PNG choice for this (Lantern-side, operator) path.

**Context.** Lantern can mint tokens and download a single token's QR as a standalone SVG (`/dashboard/qr-codes/[token]/svg`, via `buildQrSvg`), which the Operator edits and prints by hand — ADR 0015 explicitly deferred a proper N-up/sheet export to "Phase 2". The designer has now delivered an **A4 artboard carrying four counter-card design variants, each with an empty QR slot** and **all copy outlined to curves** (no `<text>`, no font references). The ask: clicking a token produces a high-quality, **print-ready PDF with the token's QR dropped into all four slots — no rasterization, no font/text blur**.

The existing self-print pipeline (`apps/web/src/lib/print-sheet.ts`, ADR 0013) can't satisfy "no rasterize": it composites an SVG card and **rasterizes it to a ~300 DPI PNG** before laying it out with pdf-lib, because **pdf-lib cannot render an SVG as vector** — it only draws its own primitives, embeds raster images, or copies pages from other PDFs. ADR 0013 chose raster because the web path had a real font/logo hazard (cross-origin logo taint); neither hazard exists here — the artboard has no fonts (outlined) and Token Print Sheets are logo-less generic stock.

**Decision.** The **SVG artboard stays the single committed source**; a build script (`pnpm --filter @repo/lantern gen:print-template`, `scripts/gen-print-template.mjs`) turns it into the runtime template:

1. **Converts the artboard SVG → a vector PDF with `rsvg-convert`** (librsvg, present on the toolchain) at an exact A4 MediaBox, and **base64-embeds** it into a generated module (`src/lib/print-template.generated.ts`) so it bundles — no runtime `fs`, no Vercel file-tracing config.
2. **Derives every `qr-code-*` slot's box** by scanning the SVG and composing each slot's full ancestor transform chain (all pure scale+translate → axis-aligned), emitting the rects (viewBox units) into the same generated module. Slots are discovered dynamically, so any count/size survives a redesign with no code change.

Then a **Lantern server route** (`/dashboard/qr-codes/[token]/pdf`, mirroring the sibling `/svg` route) loads the embedded PDF, **stamps the token's QR into each slot box with pdf-lib's `drawSvgPath`** (the QR is a single path string from `buildQrPath`; scaled `side/dim`, with a white backing rect for quiet-zone contrast), and streams it as a download (`Content-Disposition: attachment`, token code as filename).

Output is **fully vector, zero rasterization**. The Sheet is **one token across four design variants on one A4 page**, **logo-less** (generic Jugnoo-branded [Token card] stock), and is generatable for a token in **any state** (the QR encodes `/q/{token}` regardless of assignment). `pdf-lib` is added to Lantern (same version web already uses).

**Considered options.**
- **Render engine:** **vector PDF template + pdf-lib `drawSvgPath` for the QR** — chosen — vs **svg2pdf.js + jsPDF** (adds jsPDF — which ADR 0013 avoided for supply-chain posture — and re-interprets the SVG through a *second runtime* engine that can diverge on gradients/filters/masks) vs **reusing web's pdf-lib raster path** (contradicts "no rasterize / high quality") vs **server headless Chromium** (highest fidelity for arbitrary SVG, but heavy on Vercel serverless — rejected by ADR 0013). pdf-lib is the right tool to stamp the QR (a single path) but **cannot render the artboard** itself, so the artwork must arrive as a PDF.
- **Who produces the template PDF:** **a build-time `rsvg-convert` step** committed via a generated module — chosen — vs a **manual design-tool export** (originally assumed by this ADR: keeps Illustrator/Affinity as the single interpreter, but requires re-export discipline and lets the SVG master and PDF drift) vs **runtime SVG→PDF conversion** (a second interpreter in the hot path). The build-step wins because it keeps the **SVG as the one source of truth** (best DX while the artboard is still being iterated — regenerate, don't re-export), librsvg is a single high-quality *offline* converter (not a runtime engine), and the artboard is path-only + outlined so librsvg's known weak spots (fonts/exotic filters) don't bite. The cost is that librsvg, not the design tool, is the final interpreter — acceptable for an internal pilot tool; if its fidelity ever falls short, a design-tool-exported PDF can be dropped in to replace the generated one (the route is indifferent to how the committed PDF was made).
- **Template delivery:** **base64-embedded in a generated TS module** — chosen (guarantees bundling on Vercel, no `fs`/output-tracing config, matches "no CI/vercel.json" reality) — vs reading the PDF from disk at runtime (fragile under Next/serverless file tracing). Cost: a ~300 KB generated source file, regenerated by the script.
- **Generation site:** **server route** — chosen (mirrors the existing `/svg` route, keeps pdf-lib off the client bundle) — vs **client-side** like web (no upside; Lantern already does server work).
- **Scope per download:** **single token → one A4, four variants** — chosen for the first cut — vs a **multi-token batch** (N tokens → N pages), which fulfils ADR 0015's "batch sheet" phrasing in one go but needs multi-select UI + page-looping. Deferred.

**Consequences.**
- **The SVG is the single source; the PDF + slot coords are generated, not authored.** Both the embedded vector PDF and the slot rectangles come from one `gen:print-template` run; **re-run it after any artboard change** — there is no separate PDF to re-export and nothing to keep in sync by hand. The generated module is committed (no build-time conversion in CI, matching the repo's "no CI" posture).
- **The QR-slot rectangles are derived from the SVG, not hand-maintained.** pdf-lib can't read slot ids from the PDF, so the runtime stamp works off explicit rects — but the script derives them by **composing each `qr-code-*` slot's full ancestor transform chain** (the artboard nests slots several groups deep inside a clip; all transforms are scale+translate, so the resolved box stays axis-aligned), then the runtime scales viewBox units → page points (read from the loaded page) with a Y-flip. Slots are matched **case-sensitively on the `qr-code-` id prefix** (distinct from the `QR-Code-EN` card-group ids) and discovered dynamically, so a redesign with more/fewer/differently-sized slots needs no code change. The artboard's aspect must stay ~A4 (mapped edge-to-edge, ≤0.02% stretch) for the unit scale to hold.
- **No human-readable token code is printed on these sheets (deferred).** This diverges from ADR 0015's "code printed under the QR" decision and the [Scan token] glossary entry, which **remain the standing requirement** for [Token cards] generally — the divergence is scoped to the current four-variant template, which reserves no room for the code yet. Until the design is refactored to include it, the Operator reads a printed card's token by **scanning it**, and the scratched-QR / typed-assignment fallback is unavailable on these cards.
- **Diverges from ADR 0013's raster choice, for this path only.** Web self-print stays raster (its font/logo hazards are real); Lantern Token Print Sheets are vector (those hazards are absent). The two pipelines now differ deliberately — a future reader should not "unify" them without restoring web's taint/font handling.
- The web↔Lantern card machinery stays **unshared** (the QR helper was already copied, not extracted); a shared-package move remains deferred per ADR 0011/0013.
