# Operator admin gets full cross-business dashboard access; businesses stay single-owner

**Context.** During the pilot the Operator (the Jugnoo team — see [Operator]) needs to sign into the customer dashboard (`apps/web`) and monitor *any* business's data, not just operate inside Lantern. Today the dashboard resolves businesses by verified email → `User` → `user.businesses` (the `ownerId` relation; see ADR 0004), so a signed-in user only ever sees businesses they personally own. `User.role` (`OWNER` / `ADMIN`) already exists and the Operator is `role=ADMIN`, but that role does nothing in `apps/web` — it only gates Lantern's `ADMIN_EMAILS` allowlist.

**Options considered.**
- **A — Multi-owner businesses + per-user Google tokens.** Introduce a `BusinessMembership` join table (many owners per business), move OAuth tokens from `Business` to `User`, and grow Lantern onboarding to take multiple owner emails. Expressive, but a schema rebuild (new table, migration, every owner→business resolver rewritten) and a security smell: multiple people holding equal grants on one client's account. Rejected as more than the pilot needs.
- **B — Operator admin override in the resolver.** Keep `Business.ownerId` single-owner and unchanged. Branch `resolveCurrentBusiness` on `User.role`: an `ADMIN` user's candidate-business list is *every* business; an `OWNER`'s is just their own. The sidebar switcher and the active-business cookie ride that list unchanged, so an admin gets a cross-business switcher and can select any business with no new UI and no new tables.

**Decision.** Take **Option B**, full access. Businesses remain single-owner (`Business.ownerId` untouched). A `role=ADMIN` user can view **and operate** any business in the dashboard with the same rights as its owner — no per-action permission gating. The entire change is one branch in `resolveCurrentBusiness` (`apps/web/src/lib/current-business.ts`): when `role=ADMIN`, the candidate list is `prisma.business.findMany(...)` instead of `user.businesses`. The active-business cookie's "can't select a business that isn't yours" guard relaxes automatically — an admin's candidate list contains every business, so any real business id is valid.

**Why.** The Operator is the single most-trusted actor and is already admin in Lantern; read-only "monitor" mode would mean guarding every mutating action and server action for little pilot benefit, so full access is the simpler, honest choice. Option B reuses the existing `Role` enum and the email-based resolution (ADR 0004 is unchanged — admins are still resolved by verified email, they just get a wider candidate list), needs **no migration and no new tables**, and is strictly less work than Option A. Google data stays walled off without special-casing: live Reviews/Analytics + reply posting gate on a per-grant `business.manage` token (Phase 2, currently unbuilt and quota-blocked — see ADR 0003) that the admin doesn't hold, so an admin viewing another business sees everything in *our* DB (private/anonymous feedback, sentiment, taxonomy/tags, form config, QR codes, print orders) but the Google tabs show their "Connect Google"/coming-soon state. That is exactly the intended "I can monitor everything except Google reviews."

**Consequences.** An admin can mutate any client account; accepted for a single-Operator pilot, revisit if more than one admin exists or clients demand isolation (read-only mode remains a later additive option — gate mutations on "admin viewing a business they don't own"). The Operator no longer needs to be set as a business *owner* to see it — `role=ADMIN` suffices — a cleaner Operator/Owner separation. `prisma.business.findMany()` over all businesses is fine at pilot scale; revisit with search/pagination in the switcher as the business count grows.

**Role assignment.** `User.role` is resolved from the `ADMIN_EMAILS` allowlist on every web sign-in (`apps/web/src/lib/auth.ts`): an email in the list is upserted as `role=ADMIN`, everyone else as `OWNER`. This makes the env list the single source of truth — previously Lantern gated on `ADMIN_EMAILS` while `User.role` was set nowhere in code (always defaulted/written `OWNER`), so the two could drift. Resolving role on sign-in means adding/removing an email takes effect on that user's next login with no manual DB edit. Role is account-wide, **not** per-business (there is no per-business role — that was the rejected co-ownership design).

This supersedes the multi-owner direction explored before this ADR and resolves the "tokens → User" note in ADR 0003 by *not* moving tokens (admins don't need them).
