# Analysis progress is a client-driven run, not a server job

The "analyze reviews" flow is driven from the browser one batch at a time (repeated `analyzeBatchOnce` server-action calls), with live progress held in a dashboard-layout React context (`AnalysisProvider`) and shown in a persistent bottom-right widget. We deliberately did **not** build a server-tracked job: there is no `AnalysisRun` row and no background worker/queue. The existing analyzer was already client-driven, and the pilot's per-business volumes are small enough that a foreground loop is fine.

Hoisting the loop from the page (`ReviewCTA`) into the layout is what makes progress survive in-app navigation between dashboard tabs — the layout doesn't unmount when `children` swap, so the run and its widget persist.

**Consequence:** progress survives tab navigation but **not** a hard reload, a new browser tab, or closing the browser (switching the active business is itself a hard reload, so it also ends the run). This is acceptable because every completed batch is persisted, so the "X waiting" count is correct on reload and a fresh run resumes only the remainder. The run is single-flight and scoped to the current active business; the trigger is disabled while a run is live.

**Re-analyze is in place, not a wipe-then-rebuild.** "Re-analyze All" stamps the run's start time (`reanalyzeSince`) and `analyzeBatchOnce` then treats records with `analyzedAt < reanalyzeSince` (plus any `analyzedAt IS NULL`) as eligible, overwriting each as its fresh result lands. There is **no** up-front `updateMany` that clears `analyzedAt`/`tags`. This matters because the analytics dashboard reads analysed records: a bulk wipe made every analysis-derived panel (sentiment tags, operational zones, unmapped insights) go blank for the whole duration of the run on any refresh/navigation, and an interrupted re-analyze left the data wiped. In place, each record keeps its previous analysis until overwritten — the dashboard always shows a complete dataset (transiently a mix of old + new), and an interrupted run just leaves some records on their prior result. Because processed records get `analyzedAt = now` (≥ the cutoff) they drop out of the next batch, so the loop stays self-terminating and resumable; `reanalyzeSince` is held in a ref so a retried re-analyze still targets the records it hasn't refreshed yet.

Revisit if we need refresh-durable or cross-device progress, server-scheduled re-analysis, or concurrent runs across businesses — any of those would justify promoting the run to a real persisted job.
