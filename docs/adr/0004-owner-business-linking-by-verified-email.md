# Owner↔Business linking is keyed off the verified Google email, via a pre-created placeholder User

**Context.** Onboarding is operator-driven: the Jugnoo Operator hand-creates a handful of pilot businesses in Lantern *before* the owner ever logs in. The owner then signs into the customer dashboard (`apps/web`) with Google and must land on *their* business with zero claim flow or setup wizard. Two facts constrain the design: (1) `Business.ownerId` is a **required** FK to `User.id`, so a business cannot exist without a user to point at; (2) with no NextAuth database adapter, `session.userId` is the Google `sub`, **not** the Prisma `User.id` — so it cannot be trusted as a join key (this is why some API routes filtering on `ownerId: session.userId` were unreliable and `/api/generate-reply` had auth disabled).

**Options considered.**
- **A — Pre-create a placeholder User.** At onboarding the Operator creates both a `User` (email only, no name/image) and a `Business` whose `ownerId` points at it. On first sign-in the existing `signIn` callback (`prisma.user.upsert({ where: { email } })`) *finds* that waiting user and fills in name/image. Linking is implicit — it already happened at onboarding. No schema change, no nullable FK, no transient unlinked state.
- **B — `pendingOwnerEmail` + nullable `ownerId`.** Business starts unlinked (`ownerId = null`, `pendingOwnerEmail` set); a sign-in-time linking step matches the email, sets `ownerId`, clears the pending field. Adds a field, a nullable FK, an explicit link step, and an "unlinked" state to handle everywhere.

**Decision.** Take **Option A**. The Operator pre-creates a placeholder `User` + `Business` per pilot. All owner→business resolution keys off the **verified Google email**: a `getCurrentBusiness()` helper reads `session.user.email`, finds the `User` by email, and returns their `businesses` (modelled as a list; the pilot renders the first). `session.userId` is never used as a join key. A signed-in email with no matching pre-provisioned `User` sees a neutral "contact Jugnoo" holding page — never an auto-created business.

**Why.** Option A reuses machinery that already exists (the `ownerId` FK and the upsert-by-email in `signIn`), needs no migration, and has no unlinked state to reason about. Keying off the verified email rather than `session.userId` sidesteps the `sub` ≠ `User.id` mismatch entirely, and is the same key Phase 2 ("Connect Google") will use — so Phase 2 is purely additive. Modelling the return as a list keeps multi-business and multi-platform futures as added rows, not a rebuild.

**Consequences.** `User` rows can exist with an email but no name/image until the owner first logs in — a "placeholder" identity that is normal, not an error. Businesses carry a placeholder `googleLocationId` until Phase 2 (see ADR 0003). The Operator must enter the owner's email exactly; a typo means the real owner won't match and will hit the holding page (editable in Lantern before first login). API routes still filtering on `ownerId: session.userId` must be migrated to the email-based resolution to be correct. If self-serve onboarding is built later, owners creating their own `User`+`Business` is a superset of this flow, not a replacement.
