# Self-print PDF is client-side, 6-up on A4, and logo-less

**Status:** accepted — implements the Phase 2 "self-serve PDF" step of [ADR 0011](./0011-cards-graduate-to-svg-slot-injection.md), choosing a lighter path than the server renderer that ADR implied.

**Context.** ADR 0011 deferred a "self-serve composited PDF (adds a renderer dependency)" to Phase 2, implying a server route. Re-examining the artwork changed the cost picture: the Card Template SVGs carry **no `<text>` or font references** (all copy is outlined to `<path>`), so there's nothing to embed when rendering — the hardest part of a server pipeline evaporates. The one genuine hazard is the business **logo**: it's an arbitrary external URL the owner types into form settings (no upload to our domain), so rasterizing a card that contains it in the browser **taints the canvas** and the PDF export throws for any logo host without permissive CORS — i.e. most of them.

**Decision.** Ship Phase 2 self-print as a **client-side** PDF (pdf-lib + the browser canvas, ~300 DPI raster; the hairline cut grid drawn as vector lines). pdf-lib is chosen over jsPDF for its zero runtime dependencies (supply-chain posture) and because it is isomorphic — the same library serves the deferred server route below. The downloaded **Print Sheet** is a **2×3 grid of six identical QR-only cards on one A4 page**. To sidestep the canvas-taint hazard entirely, the Print Sheet is **logo-less** — it renders the Jugnoo-mark-only card; the business logo appears only on operator-fulfilled ordered cards. NFC variants stay order-only (the button is disabled with a note). The studio preview/logo toggle is unchanged (it represents the card you can *order*); the difference is labelled on the download button.

**Considered options.**
- **Generation site:** **client-side** (no server route, no shared-package move, no renderer service) — chosen for the pilot — vs a **server route (resvg-js → pdf-lib)**: more robust and reusable by Lantern in Phase 3, but heavier infra and compute the team wanted to avoid up front. Explicitly kept as the **fallback ("Option A")** if client-side proves insufficient. Headless Chromium (true vector) rejected as too heavy for Vercel serverless.
- **Logo on the sheet:** **omit it** — chosen — vs a same-origin **logo proxy** (`/api/logo-proxy`) that would keep the logo while avoiding taint (rejected as added surface for the pilot), vs **graceful fallback** on taint (rejected — silent, per-business inconsistency).
- **Sheet layout:** **6-up (2×3) on A4 with full cut-line grid** — chosen (fits the German-first market; full grid is easiest to cut straight) — vs Letter, multi-paper toggle, 4-up, or single-card-per-page.

**Consequences.** Phase 2 ships with **no new server code** and **no `injectCard`/template move into a shared package** — those are deferred with the server route to the "Option A" fallback / Phase 3. A client-only PDF lib is added to the web bundle. Self-printed cards are unbranded beyond the Jugnoo mark, which is a deliberate downgrade from ordered cards and must be communicated in the UI. If businesses demand their logo on self-print, the cheapest next step is the logo proxy (still client-side); a full server pipeline is only warranted if client-side rendering fidelity or the Phase 3 Lantern reuse forces it.
